# Polish log

Each round goes through the whole project — every simulation checked against textbook numbers and
invariants, every page used in the browser (light and dark, desktop and phone width, keyboard only),
the code read top to bottom, docs, first-run experience — then a local commit.

## Development

- [x] **Scope and stack.** A static site of interactive, step-through simulations across four areas
  (operating systems, networking, databases, distributed systems), about 8–12 topics. Every simulation
  is a pure TypeScript function from input to a list of steps (snapshot + one-sentence explanation),
  tested with `node --test` against textbook numbers and invariants; pages draw one step at a time
  through a shared player. No framework, no bundler, no runtime dependencies — `tsc` (dev dependency)
  compiles to ES modules; a 60-line Node server serves `dist/` and rebuilds on save.
- [x] **Page replacement** (`src/sim/paging.ts`, `src/topics/paging.ts`): FIFO, LRU, OPT and Clock with
  stable frame positions and a sentence per step explaining the victim. Tests: Silberschatz's reference
  string gives the textbook 15/12/9 faults; Bélády's anomaly (9 → 10 faults with more frames, FIFO);
  LRU and OPT never fault more with more frames (4 reference strings × 7 sizes); OPT is never beaten
  (5 random strings × 6 sizes × 4 policies); Clock's second chance (a case where it spares the page FIFO
  evicts — the first version of that test had the wrong expectation: Clock only spares a page whose
  bit was set *after* the hand last passed). Page: reference-string input with presets, policy
  switch, a frames × time table with hits/faults/reference bits/the hand, and a policies × 1–8 frames
  table that marks the anomaly.
  - **Found by using it**: a rebuild triggered by the watcher at the same moment as a manual build
    failed to delete `dist/` on Windows (EPERM) and crashed the dev server. The build now empties
    `dist/` instead of removing it, and the watcher keeps serving the last good build if a rebuild fails.
- [x] **CPU scheduling** (`src/sim/scheduling.ts`, `src/topics/scheduling.ts`): FCFS, SJF, SRTF, round robin and MLFQ (configurable slices per level, optional priority boost) on whole ticks, with a sentence per tick (arrivals, preemptions, demotions, boosts). Conventions stated in code and tested: a new arrival joins the queue *before* a process whose slice just ended; ties go to earlier arrival, then input order. 10 tests: the textbook averages (FCFS convoy 17 vs 3, SJF 7, SRTF 6.5 with the preemption at t=1, RR q=4 17/3); MLFQ demotion and preemption by a new top-queue job; boost ends starvation; idle ticks; and on 30 random workloads every process gets exactly its burst, never before arriving, the CPU is never idle with work waiting, SRTF has the lowest average wait of all five, SJF beats FCFS. Page: process editor with presets, a Gantt chart with run/wait/arrival marks, the queues with remaining time, per-process turnaround/waiting/response filled in as they happen, and all five policies compared.
  - **Found by using it**: the MLFQ preset showed `ui1` waiting one tick while `ui2`–`ui4` did not — correct (the batch job was still in its first top-queue slice), and a better question than the one the page asked, so the exercise now asks why.
- [x] **TCP congestion control** (`src/sim/congestion.ts`, `src/topics/congestion.ts`): a round-trip model in whole segments — slow start doubling up to `ssthresh`, additive increase, and on a loss Tahoe (always back to 1) or Reno (halve on three duplicate ACKs, 1 on a timeout); losses come from a link capacity (one dropped segment when the window exceeds it) and from scheduled timeouts. Plus two AIMD flows on one link. 9 tests: doubling and the switch at a threshold that is not a power of two, Tahoe and Reno reactions, the sawtooth (losses exactly at capacity + 1, window never below half, about 3/4 of the link delivered — the textbook figure), Reno delivers more than Tahoe, per-round consistency, and the Chiu–Jain argument checked exactly: every loss halves the gap between the two flows, increases leave it unchanged. Page: an SVG chart of cwnd and ssthresh with loss markers and the other variant as a ghost line, and a phase plot of flow A against flow B with the fairness and capacity lines.
  - **Found by using it**: with two players on one page, the arrow keys moved both. The keyboard now drives the player used last (the first one until then). A chart label sat on top of the curve's end point — moved.
- [x] **Reliable delivery** (`src/sim/transport.ts`, `src/topics/transport.ts`): the three-way handshake, a sliding window of data and the four-message teardown, tick by tick with a one-way delay, one segment per tick from the client, and losses of chosen data segments or ACK numbers (first transmission) or at random with a seed. Three recovery schemes: Go-Back-N (in-order receiver, cumulative ACKs, resend the window on timeout), Selective Repeat (buffering receiver, per-segment ACKs and timers) and TCP (cumulative ACKs, buffering receiver, one timer, fast retransmit on three duplicate ACKs). 10 tests: message order of handshake and teardown; no loss → each segment once, data right after the SYN-ACK; one lost segment → Go-Back-N resends 3–6, Selective Repeat only 3; TCP's fast retransmit comes before the timeout and finishes sooner than Go-Back-N; a lost cumulative ACK is covered by the next; Go-Back-N buffers nothing; under 25% random loss (25 seeds × 3 protocols) every segment is delivered exactly once in order, the window is never exceeded and the connection closes. Page: a sequence diagram (in-flight arrows, losses as ✕, retransmissions dashed), the client's window and the server's received/buffered segments, and the three protocols compared on the same losses.
  - **Found by testing**: a test asserting "Selective Repeat never resends more than Go-Back-N" failed — the premise was wrong twice: random losses differ between runs (the protocols send different numbers of messages), and a lost ACK *does* cost Selective Repeat a resend that a cumulative ACK would cover. Both facts now have deterministic tests, and the page asks about the second one.
  - **Found by using it**: a type error made the dev rebuild fail *after* it had emptied `dist/`, so the page went to 404 — the "keep serving the last good build" promise was false. Dev rebuilds no longer clean first and tsc runs with `noEmitOnError`; only `npm run build` starts from an empty folder. Labels of two messages sent from the same side in the same tick overlapped — now stacked.
- [x] **B+ tree** (`src/sim/bplustree.ts`, `src/topics/bplustree.ts`): insert with leaf splits (the right half's first key *copied* up) and inner splits (the middle key *moved* up), cascading to a new root; search; range scans along the leaf links; duplicates refused; every step a snapshot with the path, the new nodes and a sentence. Conventions stated (left half gets ⌈n/2⌉ keys). 8 tests: the first split by hand; an inner split does not keep its key below; every invariant after *every* step for orders 3–7 and ascending, descending and shuffled inserts (sorted nodes, separator bounds, fill limits, all leaves at one depth, the leaf chain is all keys in order); height within the logarithmic bounds for 1,000 keys; search finds all and only inserted keys, one node per level; range scans read each leaf once after one descent. Page: an SVG of the tree (path in accent, split-off nodes in red, leaf links as arrows) for building, searching and range scans, with presets.
  - **Found by testing**: the per-step invariant check failed at the moment the page deliberately shows — a parent one key over the limit, about to split in turn. The check now allows exactly that one key of slack during a split; the final tree is checked strictly.
- [x] **Transaction isolation** (`src/sim/isolation.ts`, `src/topics/isolation.ts`): an MVCC store and a typed schedule language (`T1 read x`, `T1 write x = x + 1`, `commit`, `abort`, `init`); Read Uncommitted, Read Committed, Snapshot (first committer wins) and Serializable (optimistic validation of reads and writes at commit). Row locks and waiting are not modelled, and the page says so. Every outcome is checked against all serial orders of the committed transactions (same reads, same final state). 8 tests: the four classic anomalies at each level (dirty read only at Read Uncommitted; non-repeatable read at Read Committed, not under a snapshot; lost update ends at 11 under Read Committed, aborted under Snapshot and Serializable; write skew passes Snapshot, not Serializable); skipped operations and implicit rollback; on 400 random three-transaction schedules Serializable is always serializable and Snapshot never commits two overlapping writers of one key; the weaker levels all produce anomalies. Page: anomaly presets, the interleaving table, committed state and each transaction's private writes and abort reason, a verdict with the equivalent serial order, and all four levels compared.
  - **Found by testing**: I asserted that weaker levels produce *more* non-serializable outcomes; on random schedules Read Uncommitted produced fewer than Read Committed (304 vs 362) — a dirty read of a write that later commits often looks serial. Levels are defined by which anomalies they allow, not by how often they occur; the test now says so.
- [x] **Consistent hashing** (`src/sim/hashing.ts`, `src/topics/hashing.ts`): a ring of 32-bit hash positions with virtual nodes, binary-search lookup of the first point clockwise, arc shares, modulo placement for comparison, and a replay of add/remove changes recording which keys moved. 8 tests: the hash spreads keys over the range; lookup = first point clockwise with wrap-around; adding a server moves only keys *to* it, about 1/N with 200 points; removing one moves only its keys; hash mod N moves 5/6 when going from 5 to 6 servers (the residue argument, checked); 200 points bring the busiest server under 1.1× the average where 1 point gives over 1.3×; every replayed change moves less than modulo would. Page: the ring with owner-coloured arcs, server points and keys (moved keys outlined), keys per server as bars, and busiest-over-average for 1–200 points per server against hash mod N.
  - **Checked before keeping a claim**: the code comment said plain FNV-1a clusters similar names ("A#1", "A#2") on the ring. Measured: with 200 points per server the busiest server got 1.32× the average with plain FNV-1a and 1.04× with MurmurHash3's finalizer added — the comment now gives those numbers.
- [x] **Raft** (`src/sim/raft.ts`, `src/topics/raft.ts`): leader election with seeded randomized timeouts, AppendEntries with back-off on mismatch and replacement of conflicting suffixes, commitment by majority restricted to the leader's own term, step-down on a higher term, crashes and restarts (term, vote and log persist), partitions and healing, client commands — all deterministic per seed. 9 tests, built around a checker for the paper's safety properties on every frame (one leader per term, log matching, committed entries never change and agree everywhere, commit ≤ log length): election; replication and commit to all; leader crash → new leader, higher term, log kept; a minority leader cannot commit and its entry is replaced after healing; a restarted server catches up; three servers survive one failure but not two; and 60 random schedules of crashes, restarts and partitions.
  - **Mutation-tested the checker**: removing the up-to-date vote check, allowing two votes per term, or never truncating conflicts each failed tests — but removing the Figure 8 rule (commit only own-term entries by counting) passed all 60 random schedules. Searching 3,000 found one (seed 2427) where a server commits an old-term entry that a later leader overwrites; it is now a fixed test, and the page tells this story.
  - Page: servers on a circle (leader, candidate, crashed, minority), messages in flight labelled (vote?, yes/no, ♥ heartbeat, +n entries, ok/✗), the recent events, and every server's log coloured by term with committed entries solid. Scenarios: election and replication, leader crash, split brain, catch-up after a crash (scripts can name `LEADER`, resolved by a probe run).

## Round 1

- **Independent review** (a fresh agent checked every simulation against its textbook or paper, tried edge cases the tests did not, and used the built pages in a browser): the simulations were mostly right; the problems were on the pages, in one test that checked nothing, and in some text. All fixed:
  - *The paging OPT test and the scheduling random test checked almost nothing*: their random generators multiplied past 2⁵³, so the "random" reference strings were nearly all zeros and arrivals only 0, 4 or 8. Both now use an exact Park–Miller generator; the properties (OPT never beaten, SRTF best) still hold on real random input.
  - *The scheduling page crashed* when stepping after a rejected input (11 processes): state was assigned before validation. Inputs are now parsed into locals and committed only when valid — the same fix on the paging page.
  - *The serializability check is n!*: 10 transactions froze the tab for ~15 s. Schedules are limited to 6 transactions (720 orders, instant), with a clear error.
  - *Raft*: a one-server cluster never committed (commitment only advanced on replies) — the leader now checks right after appending, and a test covers 1–7 servers; events naming a server that does not exist threw a TypeError — refused with a message; the split-brain preset was only right for 5 servers — `LEADER+MINORITY` now takes the largest minority for any size, and the page refuses fewer than 3 servers.
  - *Read Uncommitted* could return an older uncommitted write instead of a newer commit — it now returns the newest value (test). *MLFQ* reset a job's slice when it was preempted, so a long job interrupted often enough was never demoted — slices now count across preemptions (OSTEP's allotment rule; test).
  - *Pages*: "Skip to content" went through the hash router and left the topic — it now just focuses the content; Home/End/space were captured page-wide (blocking scrolling) — now only inside the player, arrows stay global; screen readers no longer hear every step while playing; the reliable-delivery comparison table threw uncaught errors when a protocol could not finish — each row is isolated and says "did not finish"; negative seeds made every packet lost — refused.
  - *Text*: B+ tree "full… half-empty" → 2 of 3 keys, a third empty; range scans now count node reads correctly (descent + leaves); SJF's optimality claim limited to jobs already waiting; snapshot isolation notes that PostgreSQL detects the conflict at the second write; `engines` raised to Node 22.18 (type stripping without a flag); the dev server answers 400 to a malformed URL instead of crashing.
- **Used every page** at phone width (375 px), in light mode, and with the keyboard only: the topic list now becomes one row of chips on a phone (current topic scrolled into view); two layout bugs made the transaction page wider than the phone (a 1fr grid column that grew with its table, and segmented buttons that could not wrap) — all nine pages now fit; the step buttons at the first/last step dropped keyboard focus when disabled — now `aria-disabled`.
- **Production build**: fresh clone → `npm install`, `npm run build`, `npm test` all pass; `dist/` served by a plain static server (not the dev server) works with no console errors.

  - *Congestion "raise ssthresh: the first loss comes from a huge window"* — never: the default 32 already overshoots the link, and doubling can never overshoot by more than 2×, so raising it changes nothing (and the model drops one segment however large the overshoot — now said).   - *Reliable delivery "spurious retransmissions appear"* — they cannot: every message takes exactly the same time, so a timer never fires early; the resends of data the server already had come from lost ACKs and Go-Back-N's going back. ## Round 3

- **Checked against the literature** (a fresh agent compared every simulation and page with RFC 5681/6298/9293, Kurose & Ross, Silberschatz, OSTEP, Bélády 1969, Berenson et al. 1995 and the PostgreSQL docs, Karger et al. and Dynamo, and the Raft paper):
  - *Raft leaders did not append the paper's no-op entry* (§8). Entries left over from an older term can only be committed together with one of the current term (Figure 8), so with seeds 2–4 the catch-up scenario stranded `r=3` on all five servers forever — while the page said the leader "fills in the rest". Leaders now start their term with a no-op; a regression test runs the scenario on 8 seeds; the logs table labels the no-ops; the tests compare client commands without them. The page's definition of *committed* ("once a majority has it") was the very thing Figure 8 refutes — now "once the leader that created it has copied it to a majority".
  - *Reliable delivery*: the teardown said "both sides are closed" — the closing side waits in TIME-WAIT (RFC 9293), now said; sequence numbers that never wrap (and why a Selective Repeat window must be at most half the number space when they do) and RFC 6298's timer backoff and Karn's rule added.
  - Smaller, stated now: Reno's window inflation during fast recovery (the chart shows where it settles), initial windows of 2–10 in real stacks; PostgreSQL runs Read Uncommitted as Read Committed; textbooks differ on what "order" means; this Raft's timeouts are short, so split votes are commoner than in a real cluster.
  - Checked and correct: every textbook number, RFC 5681's ssthresh and threshold rules, the AIMD 3/4 and Chiu–Jain arguments, Go-Back-N/Selective Repeat receiver behaviour, OSTEP's MLFQ rules, FNV-1a and fmix32 constants, Raft's Figure 2 rules.
- **Mutation testing** (`npm run mutate`, new): 42 deliberate bugs across all eight simulations — wrong victim, SJF that preempts, unbounded slow start, no fast retransmit, a lost leaf link, snapshot reads that see newer commits, a hash without its finalizer, Raft without the up-to-date vote check, without conflict truncation, without the no-op… — run in a temporary copy. All 42 make a test fail.
- End-of-round page check: all nine pages load and step to the end without errors; the Raft catch-up scenario ends fully committed on seeds 1–4 in the page itself.
- 77 tests.
